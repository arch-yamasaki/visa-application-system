# 方式② PDF page routing 実験結果（2026-08-09）

## 結論

方式②は、今回の2 fixtureでは技術的に成立しました。54 matrix callのうちAPI成功は52回で、成功した52回はすべて全ページを返し、旅券身分事項ページを1ページだけ正しく検知しました。2回は分類誤りではなくGemini APIの一時的な `ServerError` です。

ただし対象は2ケースだけなので、精度を一般化できません。本体へ接続する場合は、classifierの陰性でページを捨てないfail-open routing、API retry、候補なし・複数候補・coverage不足の人手レビューが必要です。

## 方法

- restricted fixture 2件。入力は1ケースあたりPDF 3件、32ページまたは34ページ。
- ground truthは文字が読めない縮小contact sheetを目視し、document ordinalとpage番号だけを記録。
- 9設定 × 2ケース × 3反復 = 54 matrix call。別に動作確認smoke 1 call。
- PDF direct input、structured output(JSON Schema)。氏名、旅券番号、生年月日、住所、引用本文は出力禁止。
- 生レスポンスはgit-ignored `runs/` に保存。集計JSONにファイル名と元document IDは含めない。
- automatic retryなし。API失敗はend-to-end recallでは見落としとして数える。

## 判断

第一候補は `gemini-3.5-flash-lite / MINIMAL / MEDIUM / conservative / temperature省略` です。今回の範囲では最速・最安で、6/6成功、precision/recall/exactがすべて100%でした。文書分類・routing用途に性能が十分か、ケースを広げて確認する価値があります。

3.6 Flashを使う場合の第一候補は `LOW thinking / LOW media / conservative / temperature省略` です。MEDIUMと同じ成功精度で、平均tokenは約39%減、平均推定額は約17%減でした。HIGHは今回精度向上がなく、LOWに対して約91%高価でした。

`temperature=0` は3.6/3.5系では非推奨なので送信しません。現行Previewでも省略設定が6/6、明示ゼロが5/6でしたが、差は各1系列かつ失敗はServerErrorなので、temperatureが原因とは断定しません。
