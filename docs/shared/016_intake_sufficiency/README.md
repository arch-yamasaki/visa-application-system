# 016: 情報充足チェック & 再依頼システム(インテーク)設計提案

Status: 提案(2026-07-10)。agent team調査(業務ヒアリング・既存基盤・入管制度)に基づく。

## 一言でいうと

**「フォームと書類を出してもらう → AIが『足りてる/足りてない』を判定 → 足りなければ『これをください』と具体的に依頼 → 揃うまで繰り返す」を回す仕組み。**
揃った案件だけがレビュー画面(既存visa-app)に流れてくる状態を作る。

ヒアリングで川島先生自身が語っていた理想像そのもの:
> 「自動的に書類が足りてるか足りてないかを分析します。足りてなければこれの情報くださいってリマインドします。書類もらいます。で、もう1回AIに確認させます」
> 「あらかじめ入力されたプレフィックスされたフォームのURLを渡します。で、そのフォームから回答してもらいます」
> (2026-05-01 業務ヒアリング)

## なぜ今作れるか(調査で分かった土台)

1. **「必要な情報の台帳」は既にある**: RASENSマッピング(`rasens-autofill/data/mappings/rasens_offer_mapping_v2.json`)に全122項目・必須65項目が日本語ラベル付きで定義済み。空値判定ユーティリティ(`application_data.py::is_empty_value`)もある。「必須なのに空」の機械判定は数十行で書ける
2. **判定材料も既にある**: 抽出時にAIが返す `review.missing_items / validation_errors / findings`、フィールドごとの証跡品質(`field_metadata`)、値の競合(`alternatives`)、証跡カバレッジ(`anchor_coverage`)
3. **必要書類の制度カタログが作れる**: 入管庁公式のカテゴリー1〜4別提出書類一覧(調査済み、出典付き)をデータ化すれば「書類レベルの充足」も判定できる
4. **足りないのは3つだけ**: 社外に見せる公開フォーム(トークン式)、通知(メール等)、再依頼の状態管理

## 全体像

```
[行政書士/スタッフ] 案件作成、分かっている情報を投入
        │
        ▼
  AIが充足判定 ──→ 足りている ──→ レビュー画面へ(既存フロー)
        │
     足りない
        │
        ▼
  不足リスト + 依頼文を自動生成
  「卒業証明書がありません」「職務内容の詳細が不足しています」…
        │
        ▼
  プレフィル済みフォームURLを発行し、相手(企業担当者/仲介/本人)へ送付
        │
        ▼
  相手がフォーム入力 + 書類アップロード
        │
        ▼
  提出と同時にAIが再判定(抽出→突合→充足チェック)
        │
   まだ足りない ──→ 再依頼(自動リマインド) ──→ ループ
```

## 充足判定は3層で設計する(全部AIに任せない)

| 層 | 何を見るか | 実装方式 | 例 |
|---|---|---|---|
| **L1 決定的チェック** | 必須項目の空欄、必要書類の有無(カテゴリー別) | ルール(台帳+書類カタログ)。AI不使用で誤判定なし | 「旅券番号が未入力」「カテゴリー3なのに決算書がない」 |
| **L2 整合性チェック** | 書類間の突合・矛盾 | 既存の抽出+alternatives+validation_errors を構造化 | 「履歴書と卒業証明書で学校名が違う」「契約1年なのに希望期間5年(更新予定の補足が必要)」 |
| **L3 実質判断アラート** | 関連性・専門性 | AI所見+人の判断(needs_review前提) | 「成績証明書に業務と関連する科目が見当たらない」「活動内容が単純労働に見える」 |

重要な設計原則(�アリング要件に既出):
- **「空欄」「不明」「非該当」を3状態で区別する**。「在日親族なし(確認済み)」と「未確認」は別物。フォームには「該当なし」ボタンを必ず付ける
- L1で確実に潰し、L2/L3は「人が最終判断するための材料」として出す(実務判断をAIだけで確定させない原則)

## 必要書類カタログ(L1の書類判定用データ)

入管庁公式より。カテゴリー1・2は大幅簡素化、3・4は追加書類が多い:

- 全カテゴリー共通: 申請書(様式N)、写真、返信用封筒、カテゴリー該当証明
- **カテゴリー3・4のみ**: 労働条件通知書、卒業/成績証明書(+訳文)、登記事項証明書、会社案内、決算文書、代表者申告書(2026.4.15〜)
- 該当時のみ: 専門士称号証明、派遣契約書類、CEFR B2言語証明(対人業務、2026.4.15〜)、法定調書を出せない理由資料(Cat.4)

→ `document_role`(既にmanifestにある概念)と紐付けて「この案件のカテゴリーではこの書類が未提出」を機械判定する。**案件のカテゴリー区分を入力/判定するfieldの追加が必要**(現状のcase_dataにない)。

## 段階的な作り方(3フェーズ)

### Phase 1: 社内向け充足チェック(まずここ。既存資産のみ)

- `check_completeness()`: RASENS台帳の必須65項目×空値判定+3状態管理+書類カタログ照合
- レビュー画面に「充足チェック」パネル: 不足項目リスト(日本語ラベル)+依頼文ドラフト(メール/LINE用にコピペ)
- 抽出完了時に自動実行し、`missing_fields` としてケースに保存
- **外部公開なし・通知なし**。スタッフが今のメール/LINE運用のまま、依頼文作成だけ自動化される
- 規模感: 小(バックエンド1ファイル+画面1パネル)。既存の `review.missing_items` より確実な決定的判定に置き換わる

### Phase 2: 社外提出フォーム(プレフィル+トークンURL)

- ケースごとに期限付きトークンURLを発行(`/intake/:token`)。ログイン不要、そのケースの入力だけ可能
- フォームは既知情報をプレフィル、不足項目をハイライト。「分からない」「該当なし」ボタン付き
- 書類アップロード欄(不足書類の種類を明示)
- 提出→case_dataにマージ→抽出→自動再判定→社内に通知
- 規模感: 中(公開API+フォーム画面+トークン管理)。**PII対策が肝**(後述)
- 既存資産の流用: フィールドラベル・入力型定義(`fieldPaths.ts`)、アップロードAPI、マージロジックが全部使い回せる

### Phase 3: 再依頼の自動ループ

- 不足があれば依頼メールを自動送信(フォームURL+不足リスト付き)、未提出リマインド
- workflow_stateに「入力依頼中」「再提出依頼中」を追加し、案件一覧で「待ち状態」が見える
- 通知基盤(SendGrid等)の導入。LINEは公式アカウント/Messaging APIが必要なので第2段
- 規模感: 中

## リスクと対策

| リスク | 対策 |
|---|---|
| 公開フォームURLの漏洩(PII) | 期限付き+失効可能トークン、表示は「不足項目のみ」に絞る(全データを見せない)、提出専用にして閲覧最小化、アクセスログ |
| AI判定の過信 | L1は決定的ルールのみ。L2/L3は「要確認」として人に出す。「充足OK」も人の確認を経てから申請フェーズへ |
| 「なし」と「未確認」の混同 | 3状態(空欄/不明/非該当)をデータモデルとフォームUIの両方で強制 |
| カテゴリー区分の誤り | カテゴリーは書類要件の分岐点なので、L1の最初に「カテゴリー確認」を置く(法定調書合計表等から判定補助) |
| 制度変更(2026.4.15の様式改正等) | 書類カタログをコードでなくデータ(JSON)として持ち、出典URLと日付を付けて更新可能に |
